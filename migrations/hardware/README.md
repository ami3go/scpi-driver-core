# Gated hardware sweep

Calls each driver's read-only API against a real instrument.

**This has never been run.** It was written to be read first. Every allowlist
here ships unsigned, so a fresh clone cannot sweep anything, and that is the
intended resting state.

## Why this is gated at all

`migrations/driver_api_conformance.py` sweeps every no-argument method of a
driver, and its docstring says in capital letters that it must never be pointed
at an instrument, because blindly invoking every method would enable outputs.
This directory is the version that may be pointed at one. The whole design is
the distance between those two sentences.

The failure being designed against is not a failing test. It is a supply
turning its output on into a circuit nobody was watching, or a load sinking
current from a cell that was mid-characterisation. Software cannot undo that,
so the effort goes into not doing it.

## The gates

All must pass. Each fails closed, and `gate_failures()` returns every unmet one
at once rather than the first, so setup is not a guessing game.

| # | Gate | Why |
| --- | --- | --- |
| 1 | `SCPI_HARDWARE_SWEEP=1` | Nothing runs by default or by accident. |
| 2 | `SCPI_HARDWARE_CONFIRM` equals the exact phrase | A deliberate-action token, the same idea as the core's `ConfirmationGuard`. Not a secret — it is printed in the error message. Typing it costs a moment's thought, which is the entire point. |
| 3 | `SCPI_HARDWARE_<DRIVER>_RESOURCE` | There is no default address, so a sweep cannot wander onto whatever happens to answer on the bench LAN. |
| 4 | A signed allowlist | `signed_off_by`, `signed_off_date` and `instrument_serial` all filled in. |
| 5 | The list still passes static analysis | A method added by hand is rejected unless `allow_writes` is also set — a second deliberate act. |
| 6 | `*IDN?` matches `SCPI_HARDWARE_<DRIVER>_IDENTITY` | Checked at run time before any other call. Sweeping the right list against the wrong instrument is exactly the accident the allowlist exists to prevent. |

During the run: a method the driver does not have is skipped rather than
guessed at, every call is recorded, and the sweep stops the moment the link is
lost, because continuing would pile failures onto a dead connection and hide
which call caused it.

## The allowlists

`allowlists/py_*.toml`, one per driver, generated by `generate_allowlist.py`.

They are derived, not written. Choosing safe methods by hand invites the exact
mistake this is about, so a method is proposed only when the source proves it
cannot do anything but ask questions:

- public, and callable with no arguments;
- sends at least one SCPI literal **in its own body** — delegating to a helper
  is not proof, so it is excluded;
- every literal it sends is a query ending in `?`;
- its name does not match the `DANGEROUS` pattern, applied regardless of the
  above. Belt and braces: a method could reach the instrument by a route the
  script does not model, and these are the ones that would hurt.

Current proposals — 117 methods, every one of which sends only queries:

| Driver | Proposed | Held for review |
| --- | --- | --- |
| `py_ea_ps9000t` | 29 | 28 |
| `py_agilent34411a` | 27 | 55 |
| `py_keysight_n6700` | 20 | 46 |
| `py_agilent33220a` | 18 | 54 |
| `py_ngi_n83624` | 8 | 82 |
| `py_eresistor` | 6 | 54 |
| `py_hp34401a` | 5 | 42 |
| `py_tbs1000c` | 4 | 24 |

The held-back list is commented out in each file with the reason — `writes`,
`dangerous name`, or `no visible command`. Promoting one is a manual edit plus
`allow_writes = true`, and you should record why.

The generator is conservative to a fault. `get_beeper` on the N83624 sends only
`SYSTem1:SOUNd?` and is still excluded, because its name matches `beep`. That
is the right trade: a false exclusion costs coverage, a false inclusion costs
hardware.

## Signing

Filling in the sign-off block means:

1. you have read the `read_only` list for that driver;
2. you know what is physically connected to that instrument — the serial number
   in the file is which unit you checked;
3. you accept these calls being made to it.

Sign per unit, not per model. The list is safe for an instrument on a bench
with nothing attached; the same list may not be for one wired into a fixture.

## Running it

```bash
export SCPI_HARDWARE_SWEEP=1
export SCPI_HARDWARE_CONFIRM="yes I have checked what is connected"
export SCPI_HARDWARE_PY_KEYSIGHT_N6700_RESOURCE="TCPIP0::192.168.0.13::inst0::INSTR"
export SCPI_HARDWARE_PY_KEYSIGHT_N6700_IDENTITY="N6700"

pytest migrations/hardware --hardware -k py_keysight_n6700
```

Inspect the plan first — this connects to nothing and is the intended way to
see what would happen:

```bash
python migrations/hardware/sweep.py
```

Five drivers have a verified single-call constructor. `py_hp34401a`,
`py_ngi_n83624` and `py_eresistor` do not: they take a transport object or a
GPIB address rather than a resource string. Guessing a constructor and being
wrong means connecting to something unintended, so those entries are blank and
you supply the instance yourself. `run_sweep()` takes an already-connected
driver precisely so that stays possible.

## Transcripts

Every call is appended to `transcripts/<driver>.jsonl`. That is deliberate
groundwork rather than logging for its own sake: a transcript of real traffic is
what a replay harness would be built from, and it is the thing that turns one
bench session into a regression suite that runs forever afterwards. Without it,
the traffic evaporates when the session ends.

## What is tested

`test_gates.py` — 27 tests, no hardware, safe to run anywhere. It pins that
each gate blocks, and, more importantly, that a fully configured signed setup
passes every gate: a gate that is unconditionally closed protects nothing and
hides that it was never wired up.

Verified non-vacuous the way the core is: nine gates were disabled one at a
time, and every one produced a failing test.

What is **not** tested, and cannot be until an instrument is connected: that the
connection recipes in `connectors.py` open anything. Each was checked by
importing the module in that driver's own virtualenv and confirming the
attribute exists and is callable — never by calling it, because calling it
opens a connection.
